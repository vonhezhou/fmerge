# 大文件 Diff 性能评估（2026-11-04）

本轮先落实可局部验证的内存和主线程优化。50 万行稀疏修改样本的核心比较中位数由 344 ms 降至 195 ms，独立进程峰值 RSS 中位数由 370 MiB 降至 270 MiB。全 App 仍保留完整文档、编辑器结构、行映射与历史；这些数字不代表完整编辑器的峰值或输入延迟。

## 可复现测量

- 基线为 `b1a7856` 的 `diff.dart` / `context_rows.dart`；使用相同的 `tool/benchmark_diff.dart` 生成输入。
- 本机 macOS arm64，Dart 3.13.7 AOT。每个场景运行三个独立进程，先进行小样本热身，表中为中位数。没有独占系统，适合观察趋势，不作为固定性能承诺。
- `sparse` 每 1000 行修改一行；`dense` 修改所有行。默认忽略换行，折叠上下文为前后各 10 行。
- 比较耗时只覆盖核心行级/行内比较；折叠耗时还包含构造修改行集合。RSS 是整个基准进程的峰值，包含样本生成、热身和统计，不是算法新增内存。
- 每个样本两侧各自均低于应用现有的 32 MiB 文件上限。原始测量保存在 [diff-2026-11-04.json](../tool/benchmarks/diff-2026-11-04.json)。

| 场景 | 双侧 UTF-8 输入 | 比较：优化前 → 后 | 折叠：优化前 → 后 | 峰值 RSS：优化前 → 后 |
| --- | ---: | ---: | ---: | ---: |
| 10 万行，稀疏修改 | 9.49 MiB | 68.10 → 33.97 ms | 2.88 → 3.19 ms | 98.83 → 79.14 MiB |
| 50 万行，稀疏修改 | 49.15 MiB | 344.00 → 195.34 ms | 10.45 → 9.37 ms | 370.09 → 270.34 MiB |
| 10 万行，全部修改 | 6.92 MiB | 402.71 → 402.59 ms | 5.04 → 2.67 ms | 103.97 → 96.02 MiB |

10 万行稀疏样本的折叠耗时小幅增加；区间方案主要避免大上下文配置下重复标记。全部修改场景仍触发时间预算并降级为粗区间，不能把其耗时稳定在约 400 ms 理解为精细算法已经高效完成。

```sh
dart compile exe tool/benchmark_diff.dart -o /tmp/fmerge-diff-bench
/tmp/fmerge-diff-bench 100000 sparse
/tmp/fmerge-diff-bench 500000 sparse
/tmp/fmerge-diff-bench 100000 dense
```

## 已落实的改进

1. 默认忽略换行时不再生成逐行换行匹配列表。精确文本比较直接复用分行数组，避免两份不必要的键数组。
2. 默认比较直接使用编辑器的规范化文本，避免比较前在 UI isolate 中运行换行重建。精确换行比较的重建现也随比较任务移到后台；文件保存继续执行无损换行与编码处理。
3. 行内装饰只记录真正有高亮的行。原先每个未改动行也会分配空列表和 Map 项；渲染器本来就把缺少的项视为无装饰。
4. 折叠通过合并可见区间构建映射，移除整份布尔数组与“修改行数 × 上下文行数”的重复标记；全文件修改时直接生成恒等映射。
5. 显示空白字符、字体、语法高亮与上下文行数变化不再无条件重新运行 Diff。只有比较规则改变才重新比较；已有差异文本和标记可复用。
6. 编辑器快捷键映射只在配置变化时重建，并使用新 Map 更新快捷键索引，避免旧绑定缓存残留。

只有第 1、4 项包含在上面的核心基准中。其余改进通过业务/界面回归验证，本轮没有把它们量化为整机内存或帧率收益。

## 编辑器主线程与任务调度（第二轮）

基线为 `dc76c24`。本机 macOS arm64，使用 Flutter test 的 JIT 控制器/会话环境；每个版本运行三个独立进程，每次创建两侧 10 万行文本，预热 5 次，然后执行 50 次光标移动与左右未保存状态读取。**没有加载编辑器 Widget、字形布局或绘制，不代表真实 App 的帧时间。** 峰值 RSS 包含测试环境、输入生成和控制器，不与上面的 AOT 核心进程横向比较。

| 阶段 | 每次移动及状态读取，中位数 | 测试进程峰值 RSS，中位数 |
| --- | ---: | ---: |
| 基线 | 47.73 ms | 252.38 MiB |
| 仅复用编辑器文本快照 | 18.74 ms | 213.95 MiB |
| 同时复用未保存状态判断 | 0.03 ms | 214.28 MiB |

原始数据见 [editor-2026-11-04.json](../tool/benchmarks/editor-2026-11-04.json)。基准着重测量**正文不变时**的导航成本；首次打开和实际修改后的全文快照/状态比较仍需线性工作，不能据此推断连续输入也降为 0.03 ms。

```sh
flutter --no-version-check test --no-pub --reporter expanded tool/benchmark_editor.dart
# 可通过 --dart-define=LINES=500000 改变规模，时间不做测试阈值
```

本轮进一步落实：

1. 编辑器 `text` 在文档版本不变时复用同一字符串；正文替换、输入、撤销、重做和代码行替换时失效。光标、组合区和差异布局变化不会重新拼接全文。
2. 双侧未保存状态在正文或原始保存基线变化时重新规范化、比较；格式修改仍独立计入。缓存只保留已有字符串引用与布尔结果，不额外存储一份规范化文件。指定输出时继续以输出内容为保存基线。
3. 每个会话最多一个在途比较任务，后续请求只记录需要重算，不提前持有文本快照；下一任务开始时读取最新正文和规则。受控回归中，52 次请求只执行首个与最新两个任务，峰值并发为 1。保留输入变化立即使旧结果失效的规则，并取消已被显式刷新覆盖的防抖任务。
4. 精确换行重建与三方输入比较统一在一个后台任务完成，不再由 UI isolate 执行换行映射，也不再在双侧结果返回后启动第二个三方比较任务。未改动混合换行与原文件内容保持不变。
5. 失败后可重试；过期失败不覆盖当前状态；销毁会话后丢弃排队请求和后台结果。第二轮时已经运行的 isolate 仍会自然结束；第三轮已补全局计算槽与会话销毁时的中止。

上述调度通过受控异步边界测试验证，而非用机器速度或不稳定时间阈值判断正确性。`python3 tool/check.py --native --build` 已通过，包含静态检查、146 个单元/界面用例、真实 macOS 保存/退出保护/三方合并流程，以及 51.0 MB 的 Release 构建；真实中文输入法仍需人工验收。

## 五项剩余热点优化（第三轮）

基线为 `69c488e`。本轮五项均有实际改动，完成范围如下：

| 项目 | 已实现 | 仍需区分的边界 |
| --- | --- | --- |
| 跨会话调度 | 全 App 一个计算槽；排队时只保留快照工厂，在真正启动时读取最新正文与代次；关闭会话会移除排队工作，并以 `Isolate.immediate` 中止其比较 isolate。错误退出、快照失败和取消均会释放槽位。 | 文件读写后台任务不占比较槽，也不因关闭窗口而强制中断原子保存。当前每次比较仍创建 isolate，未改成长驻 worker。 |
| 编辑与文件处理 | 保留第二轮快照复用；读取、解码、摘要计算、保存时的换行映射/编码/文件冲突校验与原子写入移到后台。成功后才更新主线程文件模型，保留保存期间新输入和无 BOM UTF-16 等规则。 | 第三轮时实际修改仍触发全文字符串和未保存判断；第四轮已移除双栏局部按键的这些读取，见下节。比较/保存快照及三方初始计划仍需全文工作。 |
| 行模型与索引 | 大文件稀疏修改只持久保留左右 `Int32List` 索引与变化行对象；未修改行读取时生成视图。布局直接读取索引、只遍历变化行；折叠索引改用定长整数数组，隐藏行按连续区间存储。 | 分行和完整正文仍保留；该方案减少常驻对象，不保证所有核心进程的瞬时 RSS 都下降。 |
| 密集修改 | 大片低相似度文本使用唯一精确文本锚点及最长递增子序列分段；重复行不能充当唯一锚点，无共同键时直接得到完整替换。小范围和稀疏修改沿用 Myers。超过 2048 视觉行的单个修改块使用整行高亮，避免耗尽逐行细化预算。 | 大重写块有意减少行内高亮细节，状态栏保留简化提示；采用、复制、保存保留完整文本。锚点分段不承诺全局最短编辑路径；三方合并状态机继续使用原来的 Myers 规则。 |
| 缓存、历史与实测 | 段落缓存改为 LRU，最多 512 项且原始文本合计不超过 1 Mi 字符；超长键也计入预算。双栏撤销历史默认最多 200 个状态，并受 32 Mi UTF-16 字符的保守状态总量预算限制，至少保留一次撤销。增加真实 Release 打开/编辑/撤销/远距离滚动/三次重载测量。 | 字符预算不是精确堆字节数，至少两个状态可能超过预算；状态中的共享结构不能按简单字符量推断真实内存。仍在绘制的段落不提前 dispose，移除缓存引用后交由回收；本轮不声称完成 GC 稳态或真实中文输入法验收。 |

## 实际编辑与帧时间优化（第四轮）

基线为 `0a67c76`。此次关注真实编辑链路，而非只读光标移动基准：

1. 文档段缓存行数和 UTF-16 字符数，复制未改动段时复用统计，只重算变动段。历史预算使用分段统计，不再为记录一次输入读取全文。
2. 双栏变更监听和未保存判断直接比较持久化分段文档。先比较精确长度/行数，再按共享段与原始文本比较，不用哈希相等代替内容相等。保存基线变化后会重新解析一次基线；折叠与分段分布变化保持正文语义不变。
3. 没有折叠子行的普通行直接返回自身文本，避免全文快照时为每行构造临时列表。局部输入、光标、组合区和撤销事件不再为双栏通知/未保存判断拼接全文；比较防抖到期或保存时仍会创建完整快照。
4. 超出高亮大小上限直接按可见行显示纯文本，不再发送整份文档和构建全文纯文本高亮树；阈值内的行长度检查改为顺序遍历，过期后台结果不能覆盖新文档。
5. 折叠布局显式保存可见真实行索引，渲染按可见索引二分定位，不逐行扫描长隐藏区；隐藏真实行通过区间映射查询，不再创建每行一个条目的隐藏集合。
6. 光标、输入法组合区与折叠本身不再新增正文撤销记录，撤销后移动光标也不会清空重做分支。

新增回归中，未改动行的序列化函数被设为抛错，验证局部输入、组合区、未保存判断、撤销和重做确实无需序列化；随机编辑覆盖跨行粘贴、分段拷贝、字符统计和 Unicode。折叠渲染测试通过操作计数验证不会遍历 9800 行隐藏内容，而非依赖时间阈值。

### 帧统计口径更正

Flutter Release 的 `FrameTiming` 约每秒批量送达。旧脚本仅在滚动前清空列表，收到的批次仍可能包含前序编辑/比较帧，先前约 25 ms 的值不能当成纯滚动帧指标。本轮用 `rasterFinishWallTime` 和引擎阶段时间差推导构建开始的墙钟时间，仅纳入真正发生在滚动区间的帧，并等待批量报告送达。

同一修正版脚本分别在基线和最终代码中运行；不能把修正脚本自身带来的数值变化算成产品提速。旧的未筛选过程数据以 `unfilteredBefore` / `unfilteredAfter` 保留。新对照见 [native-fourth-2026-11-04.json](../tool/benchmarks/native-fourth-2026-11-04.json)。
